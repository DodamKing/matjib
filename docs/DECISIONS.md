# 설계 결정 기록 (ADR-lite)

새 결정이 생기면 맨 아래에 추가. "왜"를 남겨서 재토론(=토큰 낭비)을 막는 게 목적.

## D1. 기술 스택: Next.js + TypeScript (풀스택)
- **결정**: 별도 백엔드 없이 Next.js App Router 한 프로젝트로.
- **왜**: 원클릭 웹 진입 = 웹앱 본질에 맞음. API Route로 키를 숨긴 채 외부 API 호출 가능.
  현재 규모(API 호출 몇 개)에 FastAPI 등 분리 백엔드는 과함.

## D2. 1차 데이터 소스: 소상공인시장진흥공단 상가(상권)정보 API
- **결정**: 공공데이터포털의 「반경내 상가업소 조회」를 1차 소스로 사용.
- **실 API 검증됨 (2026-07-09, 키 발급 후)**:
  - 엔드포인트: `https://apis.data.go.kr/B553077/api/open/sdsc2/storeListInRadius`
    (구버전 `sdsc`는 "API not found" — **폐기됨. sdsc2 사용**)
  - 요청: `serviceKey` + `radius`(m) + `cx`(경도, =lng) + `cy`(위도, =lat) + `indsLclsCd` + `numOfRows` + `pageNo` + `type=json`
    (⚠️ cx=경도/cy=위도로 축이 뒤집혀 있음)
  - **음식 대분류 코드 = `I2`** (sdsc2 신분류). 서버 필터로 음식점만 조회됨(강남 500m→1,154개).
  - 응답 필드: `bizesId`→id, `bizesNm`→name, `indsSclsNm`→category(소분류명), `lon`→lng, `lat`→lat,
    `rdnmAdr`(도로명)/`lnoAdr`(지번)→address. 게이트웨이 오류는 평문("Forbidden")/XML로 오므로 JSON 파싱 방어 필요.
  - 무료. 활용신청 자동승인이나 **키 활성화까지 최대 1시간**(그전엔 "Forbidden").
- **출처**: https://www.data.go.kr/data/15012005/openapi.do

## D3. ⚠️ 데이터 함정: 품질/평점 신호 없음 → "최적"의 정의를 바꾼다
- **사실**: 위 데이터는 국세청·카드사 기반 "등록 정보". 리뷰·평점·맛 품질 신호가 **전혀 없음**. 분기 갱신.
- **결정**: "광고 제외 최적의 3개"에서 *최적*을 품질로 정하지 않는다.
  정렬/선정 = **거리 + 업종 적합도 + 공정 셔플(랜덤 추첨)**.
- **왜 괜찮은가**: 기획서 USP(차별점 3 "평점 조작 없는 플랫·공정 데이터")와 오히려 일치.
  컨셉을 "AI가 맛집을 고른다" → "AI가 상황을 진단해 가까운 곳을 공정하게 처방한다"로 정렬.

## D4. 상호명+좌표 보강 = 지도/길찾기 링크용 (평점 랭킹 비목표)
- **결정**: 공공데이터로 후보(좌표·거리·업종) 확보 → 상호명+좌표로 카카오 로컬 API 재조회해
  **길찾기/상세 링크·정확 주소·전화**를 보강. **선택적(fallback)**: 매칭 실패 시 공공데이터만으로 카드 표시.
- **하지 않는 것**: 평점/리뷰 수집(스크래핑 포함). USP와 충돌하고 ToS 위험. 퍼지 매칭이라 품질 근거로 부적합.

## D5. 상황 매칭 = 자연어+LLM 대신 "상황 태그" 다중 선택 (2026-07-07 개정)
- **원 결정(폐기)**: Claude API로 자연어("비 오는데 뜨끈한 면") → 업종 소분류/키워드 변환.
- **바뀐 결정**: 자유 입력 없이 고정 태그 8개(해장/든든하게/가볍게/매콤하게/뜨끈한 국물/이국음식/
  분위기 있게/빠르게 한끼, `lib/tags.ts`) 중 다중 선택 → 키워드로 `Restaurant.category` 필터링
  (`lib/match.ts: filterByTags`). LLM 호출 없음, 순수 클라이언트 로직.
- **왜**: (1) 제품 원칙 "원클릭·선택지 축소"에 자유 입력보다 태그 클릭이 더 부합.
  (2) LLM 키·지연·비용 없이 결정론적으로 동작. (3) 태그 개수를 늘려 전체 업종을 커버하려 하면
  선택지가 다시 늘어나 정체성이 깨짐 — 대신 태그 미매칭/미선택은 "아무거나"로 처리하고
  D3의 공정 셔플이 롱테일 카테고리(예: 치킨, 냉면)를 흡수한다. 커버리지보다 선택 속도 우선.
- **파생 효과**: 매칭에 서버가 필요 없어져 `/api/recommend`는 Phase 3(실데이터 조회, 키 은닉)까지
  불필요 — Phase 2는 전부 클라이언트(`app/page.tsx`)에서 처리.
- **페르소나**: 결과 카피("AI 의사 처방" 톤)도 LLM 대신 템플릿 문자열(`lib/persona.ts`)로 생성.
  선택된 태그가 있으면 카피에 반영, 없으면 일반 문구 중 랜덤.

## D6. API 키는 서버에서만
- **결정**: 공공데이터/카카오 키는 API Route(서버)에서만 사용. 클라이언트 노출 금지.
  (Anthropic 키는 D5 개정으로 v1에서 미사용)

## D7. 런타임 로깅 = console만, 외부 모니터링 서비스 없음
- **결정**: 클라이언트 에러(예: geolocation 실패)는 `console.error`로만 남긴다.
  Sentry 등 외부 에러 모니터링 서비스는 v1에서 붙이지 않는다.
- **왜**: 개인/소규모 프로젝트 단계 — 무료 티어 밖 비용·설정 오버헤드 대비 얻는 가치가 낮음.
  사용자 계정이 없어 에러를 특정 유저에 연결할 필요도 없음. 트래픽이 늘거나 운영 이슈가
  실제로 생기면 그때 재검토.

## D8. 실행 순서 재배치: Phase 4 → 공공데이터 키+Phase 3 → 카카오 고도화 (2026-07-07)
- **결정**: ROADMAP 번호(Phase 0~4)는 그대로 두되, 실제 착수 순서는
  Phase 4(상태처리/로깅, 배포 제외) → 공공데이터 키 발급 후 Phase 3 핵심(`sangwon.ts`)
  → 카카오 로컬 API 고도화(`kakao.ts`, 원래도 선택 항목) 순으로 진행.
- **왜**: Phase 4의 상태처리·로깅은 실데이터 유무와 무관하게 지금 끝낼 수 있고, 공공데이터
  키는 아직 미발급 상태라 대기 시간에 먼저 처리하는 게 합리적. Vercel 배포만은 사용자 지시가
  있을 때 진행(외부 배포는 되돌리기 번거로운 행동이라 별도 확인 필요).

## D9. Phase 3 오케스트레이션: 서버 조회 + 셔플 풀 상한 20 (2026-07-09)
- **결정**: 실데이터 흐름을 `/api/recommend`(서버)로 이전. `POST {lat,lng,radius,tags}` →
  `sangwon.searchInRadius`(음식 조회) → `buildPool`(거리순) → `filterByTags` → **거리순 상위 20개**를
  풀로 반환하고 그중 `pickThree`한 3카드도 함께 반환. 클라(`page.tsx`)는 셔플 시 재요청 없이
  반환된 풀로 로컬 `pickThree`만 한다. (`RecommendResponse`: `poolToken` → `pool: Restaurant[]`)
- **왜 서버로**: 실데이터부턴 공공데이터 키 은닉이 필요(D6). 매칭 자체는 D5로 LLM이 빠졌지만
  키 호출 지점이 생겨 서버 레이어가 필요해짐.
- **왜 상위 20**: 강남 등 밀집지는 반경 내 음식점이 1,000+개 → 전부 셔플하면 "걸어서 가까운" 원칙이
  깨짐. 거리순 상위 20으로 캡하면 어떤 조합이 나와도 전부 도보 1~3분권 + 셔플 신선함 유지 + 페이로드 경량.
- **알려진 한계**: API가 페이지당 최대 1,000개(numOfRows 상한)라 초밀집 반경(예: 강남 600m>1,000개)에선
  최근접 일부가 누락될 이론적 여지. 실측상 상위 결과가 전부 1~2분권이라 실질 영향 없음 — 페이징은
  MVP에서 도입 안 함. 문제되면 그때 다중 페이지 조회로 확장.
- **위치 거부 폴백**: 더미 식당배열(`MOCK_RESTAURANTS`)은 제품 경로에서 제거. 위치 거부 시
  `MOCK_CENTER`(강남역) 좌표로 **동일한 실 API**를 호출한다. `mock.ts`는 개발/오프라인용으로만 보존.

## D10. 검색 모드 분리: 밥집 / 카페 / 술집 (2026-07-09)
- **문제**: 공공데이터 음식 대분류(I2) 안에 **카페(비알코올)·주점(술집)이 섞여 있어서**,
  밥집을 찾는데 커피숍이 상위에 뜸(특히 밀집지 무태그일 때 카페가 밥집을 밀어냄).
- **결정**: 상단 **모드 토글(🍚 밥집 / ☕ 카페 / 🍺 술집)** 추가, 기본=밥집. 소분류명으로 3모드 분리
  (`lib/modes.ts`): 카페=`카페`·`빵/도넛`·`아이스크림/빙수`, 술집=주점류 4종, 나머지 전부=밥집.
  상황 태그도 **모드별 세트**(`MEAL_TAGS`/`CAFE_TAGS`/`BAR_TAGS`)로 분리, 모드 전환 시 선택 태그 초기화.
- **왜 원칙 안 깨지나**: 기본이 밥집이라 원클릭 진입 유지. Zero-Scroll·3카드·랭킹없음·무광고 그대로.
  선택지가 느는 우려는 있으나 "무엇을 찾나"는 단일 최상위 선택이라 리스트가 아님 — 허용선으로 판단.
- **파생**: `filterByTags`가 모드 태그셋을 인자로 받도록 일반화. `'가볍게'` 태그에서 `카페` 키워드 제거
  (이제 카페는 별도 모드). **페르소나 카피(`lib/persona.ts`) 삭제** — 헤더/태그칩과 중복이라 미사용 확정(D5 페르소나 항목 폐기).
- **스코프**: "식당 편"을 넘어 카페/술집까지 포함하도록 MVP 범위를 의식적으로 확장(MVP_SCOPE 갱신).

## D11. 길찾기 = 외부 앱 즉시 이탈 → 앱 내부 상세 시트로 감싸기 (2026-07-09)
- **문제**: 카드의 "길찾기"가 곧장 `map.kakao.com` 새 탭으로 튕겨 브랜드 밖으로 이탈. 사용자가 어디로
  가는지(방향·거리) 확인 없이 바로 외부로 나감.
- **결정**: 카드 길찾기 → **앱 안에서 올라오는 장소 상세 바텀시트(`PlaceSheet`)**로 감싼다.
  시트 = 미니 로케이터(방향·거리·도보) + 상호/업종 + 주소 복사 + **내비앱 선택**. 최종 외부 진입만
  사용자가 고른 앱으로 일어남(의도된 핸드오프). 배경 딤·ESC·배경 스크롤 잠금·슬라이드업(reduced-motion 대응).
- **키 없이 v1**: 지도 미리보기는 **실지도 타일 대신 방향(나침반 화살표)+거리** 미니 로케이터로 —
  기존 `haversine`에 `bearingDeg`/`compass8`(8방위 한글)만 추가하면 되고 **키가 전혀 필요 없다**.
  내비앱 딥링크도 키 불필요: 카카오맵 `link/to`(웹·앱), 네이버 `nmap://route/walk`(appname은 식별자, 키 아님).
- **내비앱 = 카카오맵·네이버지도 2종**(티맵 제외): 걸어서 5~15분권 서비스라 **도보 길찾기** 지원 앱만 노출,
  차량 내비(티맵)는 컨셉과 안 맞아 뺀다. 추가는 `lib/navlinks.ts`에 함수 하나씩이면 됨.
- **실지도 미리보기 = NCP Static Map 채택·구현·라이브 검증 완료**(2026-07-09): 서버 전용 키로 **`/api/staticmap`** 프록시.
  키는 서버에만(D6 유지). Kakao 정적지도는 JS SDK=클라 키뿐이라 D6와 충돌 → 미채택.
  **키 미설정이면 501 → PlaceSheet가 `<img>` onError로 받아 방향·거리 로케이터로 자동 폴백** → 앱 안 깨짐.
- **NCP 실측 함정 2개(2026-07-09, 강남 좌표로 확인)**:
  - 엔드포인트는 **신 플랫폼 `maps.apigw.ntruss.com/map-static/v2/raster`** 사용. 구 `naveropenapi.apigw.ntruss.com`은
    신규(2026) 자격증명에 **401**. 헤더는 `x-ncp-apigw-api-key-id`/`x-ncp-apigw-api-key`(대소문자 무관).
  - 마커 **`type:e`는 403**으로 거부됨 → 식당·내위치 **둘 다 `type:d`**(색상만 주황/파랑 구분). markers만 주면 두 점 자동 프레이밍.
  - 검증: 라우트가 200 `image/png`(scale=2, 1200×640) 반환, 강남역=파랑·식당=주황 마커로 실지도 표시 확인.
- **원칙 유지**: Zero-Scroll(시트도 한 화면)·서버 전용 키·무랭킹·무광고·원클릭 그대로. `lib/kakao.ts`
  (좌표 보강)와는 별개 — 이번 건은 링크 UX 감싸기이지 데이터 보강이 아님.

## D12. 지도 SDK 클라이언트 키(Dynamic Map) = D6의 명시적 예외 (도메인 제한으로 보호) (2026-07-09)
- **배경**: 시트 지도 썸네일 **탭 → 전체화면 인터랙티브 지도**(핀줌·이동) = NAVER **Web Dynamic Map**.
  이건 브라우저에서 JS SDK로 로드돼 **클라이언트 키 노출이 구조상 불가피**(모든 지도 SDK 공통: 구글맵·카카오맵도 동일).
- **결정**: 지도 SDK JS 키는 시크릿이 아니라 **공개 키**(도메인/Referer 제한이 보호수단). 따라서 D6("키는 서버에서만")·
  CLAUDE.md("`NEXT_PUBLIC_` 금지")의 **명시적 예외**로, `NEXT_PUBLIC_NCP_MAP_CLIENT_ID`로 클라 노출 허용.
  ⚠️ 예외는 **지도 SDK JS 키 한정** — Static Map 시크릿(`NCP_MAP_CLIENT_SECRET`)·공공데이터 키는 여전히 서버 전용.
- **보호 방식**: NCP Application의 **Web 서비스 URL**에 등록된 도메인(localhost + 배포도메인)에서만 지도가 렌더됨.
  미등록 도메인은 `navermap_authFailure` → MapModal이 안내 표시. 남이 키를 복사해도 자기 도메인에선 무효.

## D14. 도보 시간 = 누적 반경 → 겹치지 않는 구간(밴드) (2026-07-13)

  어떤 버튼을 눌러도 **거의 다 도보 1분 미만**만 뽑혀 버튼이 사실상 무의미했음. 구간으로 나누면 "조금 더 멀리
  걷더라도 다른 동네"를 실제로 탐색할 수 있음.
- **구현**: 밴드 = walkMin(=round(m/80)) 기준 필터 `minMin < walkMin <= maxMin` (`lib/walkBands.ts` 단일 원천).

- **부작용**: 밀집하지 않은 지역에서 10분·15분 구간이 비어 "이 도보 구간엔 없어요"가 뜰 수 있음(정상 — 다른

## D22. API 남용 대응의 최종형 = NCP 콘솔 한도(진짜 천장). 코드는 동결 (2026-07-17)

## D23. 릴스 앱 화면은 9:16(576×1024) 프로덕션 빌드로 직접 녹화 — 크롭 금지 (2026-07-17)

**결정**: `record-reel.mjs`는 **576×1024(정확히 9:16) 뷰포트 + 프로덕션 서버**로 녹화하고, `assemble.sh`는
크롭하지 않는다. 1080폭 정규화는 `prep-recording.sh`(ffmpeg)가 한다.

**왜** — 기존엔 폰 비율(390×844=0.462)로 찍고 `crop=1080:1920:0:140`으로 9:16(0.5625)에 맞췄는데,
세로 418px(18%)이 잘리면서 **브랜드 태그라인 "맛집 안 찾아줍니다"가 글자 중간에서 잘리고, 모드 탭은
28px만 남고, 도보 탭은 통째로 사라졌다.** 대본 컷3이 파는 "밥집, 걸어서 10분"의 증거가 릴스에 없었다.

**기각한 대안**:
- **세로를 줄여 9:16 맞추기(390×693)**: 안 된다. 앱 콘텐츠 높이는 뷰포트에 따라 **리플로우되지 않아**
  (측정: 어느 뷰포트에서도 도보 탭 하단 = 839px 고정) 잘리는 위치만 ffmpeg → 브라우저로 옮겨간다.
- **ffmpeg 레터박스**: 되지만 앱이 18% 축소되고 여백이 생긴다. 가로를 넓히면 앱이 max-width로 가운데
  정렬되며 남는 폭이 **같은 배경색(#fffbeb)** 으로 차서 여백처럼 안 보이므로 이쪽이 낫다.
- **`recordVideo.size`를 1080×1920으로 키우기**: **안 된다.** playwright는 페이지를 축소만 하고 **확대하지
  않는다** — 576×1024 페이지가 좌상단에 원본 크기로 박히고 나머지가 회색이 된다(실측). size는 뷰포트와
  같게 두고 ffmpeg으로 확대한다.

**프로덕션 빌드로 녹화하는 이유**: dev 서버는 Next.js dev 인디케이터(**N 배지**)를 영상에 남긴다. 예전
crop이 이걸 우연히 가리고 있었을 뿐이라, crop을 없애자 릴스에 드러났다. `record-reel.mjs`가 `nextjs-portal`을
감지해 dev면 중단시킨다.

**페이싱**: 셔플 클릭 간격 1700ms → **3200ms**(롤 800 + 정지 2400). 예전엔 3곳이 멈춘 뒤 읽을 시간이
900ms뿐이라 클라이맥스가 깜빡이고 지나갔다. 앱 컷은 롤 직전에 시작해 **정지 구간에서 끝나야** 한다.

**교훈(반복해서 어긴 것)**: 렌더 산출물은 **1080×1920 프레임 전체를 눈으로** 확인해야 한다. 축소 타일과
샘플 몇 장으로 "검수했다"고 두 번 보고했고, 두 번 다 틀렸다(첫 번째는 잘림을, 두 번째는 화면 절반의 회색
여백과 N 배지를 놓쳤다 — 회색을 보고도 "타일 패딩이겠지"라고 넘겼다). 검수 항목은 `marketing/README.md`.

- **앱 화면에 브랜드 표기가 아예 없었다** → 릴스·검색으로 온 사람이 각인할 이름이 없음.

**"딱세곳" 선정 기준**(사용자: "브랜드명 중요치 않고 중복 없이 검색만 되면 됨"): 제품 약속("딱 3곳")을
이름이 그대로 말하고, 3음절이라 구전·핸들에 유리. **검색 충돌 실측**: DuckDuckGo 정확일치(`"딱세곳"`)
**0건** — 그 토큰을 이름으로 쓰는 곳이 없음. (네이버 직접 조회는 봇 차단으로 불가 — 게시 전 사람이 최종 확인 권장.)

**브랜드 마크** = `app/icon.svg`의 **카드 3장 부채꼴 심볼을 승격**. 이미 존재하는 자산이고 릴스·캐러셀
클라이맥스(3장 카드)와 같은 정체성이라 새로 만들 필요가 없었다. `components/BrandMark.tsx`(심볼+워드마크)로
빼서 앱 헤더 최상단에 둠. 층위: **딱세곳**(브랜드) → "맛집 안 찾아줍니다"(제품 약속) → 설명.

**OG 한글 폰트 버그 동시 수정**: `app/opengraph-image.tsx`가 `loadKoreanFont()`를 안 써서 배포(Vercel
리눅스)에서 한글이 두부(□)로 깨질 상태였다(로컬 Windows는 시스템 폰트로 우연히 렌더돼 안 보였음).
share OG는 이미 폰트를 실었는데 메인 OG만 누락 — Pretendard 로더 추가로 통일. 파일 크기 변화(34518→34765)로
실제 적용 확인. 겸사겸사 메인 OG 문구 "🩺 오늘 뭐 먹지 클리닉"(D18이 폐기한 메뉴 프레임)도 브랜드명+장소 프레임으로 교체.

**유지한 것**: `lib/navlinks.ts`의 `appname=matjib`(네이버지도 앱 스킴 기술 식별자)은 그대로. 브랜드 표기가
아니라 등록 스킴과 얽힐 수 있는 식별자라, 잘못 바꾸면 길찾기가 깨진다. 네이버 앱의 "돌아가기" 라벨 노출
여부는 미검증 — 필요 시 별도 확인.

## D25. 마케팅 에셋 브랜드 갱신 + CTA를 포맷별로 분리(릴스=검색 / 캐러셀=프로필링크) (2026-07-18)
> D24의 후속(앱은 딱세곳으로 바뀌었으나 마케팅 에셋은 낡아 있었음).

**결정 1 — 마크 통일**: 캐러셀(`marketing/carousel/slides.html`)·릴스 카드(`marketing/reel/cards.html`)의
브랜드 마크를 예전 "주황 점(dot)+matjib"에서 **앱 `BrandMark`와 동일한 카드 3장 심볼 + "딱세곳"**으로 교체.
문서에 `<symbol id="mark3">` 한 번 정의 후 `<use>`로 참조(반복 제거). 앱 아이콘과 픽셀 단위 동일 자산.

**결정 2 — CTA를 포맷별로 분리**(이게 핵심):
- **릴스 CTA = "🔍 딱세곳 검색"**. **캐러셀 CTA = "프로필 링크 → 딱세곳"**. (raw 도메인 `matjib.dimad.kr`을
  CTA에 박던 것 폐기 — "아무도 도메인 안 친다"(사용자). 캡션의 도메인 언급은 백업으로 유지.)
- **왜 갈랐나**: ① **게시 타이밍**이 다르다 — 캐러셀은 검색확인 전 근시일 업로드, 릴스는 **업로드 자체를
  "딱세곳 검색 실노출 확인"에 게이트**. ② **도달 방식**이 다르다 — 릴스는 알고리즘이 팔로워 아닌 콜드 유저에게
  뿌려서 스크롤 중 프로필 탭을 잘 안 함 → 이름을 기억했다 **검색**하는 행동에 맞음. 캐러셀은 프로필 방문자가
  보는 포맷 → 링크 탭이 자연스러움. ③ "프로필 링크"만 쓰면, 프로필이 **여러 링크를 담은 허브(점점 많아짐)**라
  거기서 딱세곳을 찾게 만들어 이탈 지점이 됨 → CTA가 목적지를 지목하거나(캐러셀) 검색으로 우회(릴스)해야 함.
- **전제 실측(2026-07-18)**: 색인 요청은 넣었으나 **구글에서 "딱세곳" 검색 시 사이트 미노출**(무관한 슬랭·레시피만).
  네이버는 검색 페이지 봇 차단으로 직접 확인 불가(외부 도메인을 더 늦게 잡으므로 거의 확실히 미노출). → 검색 CTA는
  릴스에 미리 박아두되 **업로드 전 재검색해서 실제 노출 확인** 필수. 그때도 안 뜨면 릴스 CTA도 프로필링크로 회귀(한 줄 교체).

**결정 3 — 앱 데모에 워드마크는 안 넣음**: 재녹화로 D24 헤더(딱세곳 BrandMark)를 릴스 데모에 넣으려 했으나,
**9:16 세로 폭에선 3곳 카드+셔플 버튼(핵심 메커니즘)과 상단 워드마크가 한 프레임에 못 들어간다**(콘텐츠가
뷰포트보다 길어 셔플을 보여주면 워드마크가 스크롤 밖). → 데모는 **메커니즘 우선**, 워드마크는 **훅+CTA 카드**(영상
여닫는 자리)가 담당. 데모 상단엔 포지셔닝 문구 "맛집 안 찾아줍니다 / 갈 데를 정해줍니다"가 노출됨. 억지로 넣으면
셔플·탭이 프레임 밖으로 나가 데모가 약해짐.

**재녹화**: `marketing/reel/reel-shuffle.mp4`(커밋 편집 소스)를 현재 프로덕션 빌드로 재녹화(강남역 실데이터).
