## D1. 기술 스택: Next.js + TypeScript (풀스택)
- **결정**: 별도 백엔드 없이 Next.js App Router 한 프로젝트로.
- **왜**: 원클릭 웹 진입 = 웹앱 본질에 맞음. API Route로 키를 숨긴 채 외부 API 호출 가능.
  현재 규모(API 호출 몇 개)에 FastAPI 등 분리 백엔드는 과함.

## D2. 1차 데이터 소스: 소상공인시장진흥공단 상가(상권)정보 API
- **결정**: 공공데이터포털의 「반경내 상가업소 조회」를 1차 소스로 사용.
- **검증됨 (2026-06-19)**:
  - 요청: `radius`(m) + `cx`(경도) + `cy`(위도) + `indsLclsCd`(업종 대분류)
  - 응답: 상호명, 상권업종(대/중/소분류), 경도/위도, 주소
  - 업종 분류: 대분류 10 / 중분류 75 / 소분류 247. 음식 대분류로 식당 필터, 소분류로 면/국밥 등 세분 매칭.
  - 무료. data.go.kr 가입 + API 신청 → 보통 1~2시간 내 키 발급.
- **출처**: https://www.data.go.kr/data/15012005/openapi.do

## D3. ⚠️ 데이터 함정: 품질/평점 신호 없음 → "최적"의 정의를 바꾼다
- **사실**: 위 데이터는 국세청·카드사 기반 "등록 정보". 리뷰·평점·맛 품질 신호가 **전혀 없음**. 분기 갱신.
- **결정**: "광고 제외 최적의 3개"에서 *최적*을 품질로 정하지 않는다.
  정렬/선정 = **거리 + 업종 적합도 + 공정 셔플(랜덤 추첨)**.
- **왜 괜찮은가**: 기획서 USP(차별점 3 "평점 조작 없는 플랫·공정 데이터")와 오히려 일치.
  컨셉을 "AI가 맛집을 고른다" → "AI가 상황을 진단해 가까운 곳을 공정하게 처방한다"로 정렬.

## D4. 상호명+좌표 보강 = 지도/길찾기 링크용 (평점 랭킹 비목표)
- **결정**: 공공데이터로 후보(좌표·거리·업종) 확보 → 상호명+좌표로 카카오 로컬 API 재조회해
  **길찾기/상세 링크·정확 주소·전화**를 보강. **선택적(fallback)**: 매칭 실패 시 공공데이터만으로 카드 표시.
- **하지 않는 것**: 평점/리뷰 수집(스크래핑 포함). USP와 충돌하고 ToS 위험. 퍼지 매칭이라 품질 근거로 부적합.

## D5. 상황 매칭 = 자연어+LLM 대신 "상황 태그" 다중 선택 (2026-07-07 개정)
- **원 결정(폐기)**: Claude API로 자연어("비 오는데 뜨끈한 면") → 업종 소분류/키워드 변환.
- **바뀐 결정**: 자유 입력 없이 고정 태그 8개(해장/든든하게/가볍게/매콤하게/뜨끈한 국물/이국음식/
  분위기 있게/빠르게 한끼, `lib/tags.ts`) 중 다중 선택 → 키워드로 `Restaurant.category` 필터링
  (`lib/match.ts: filterByTags`). LLM 호출 없음, 순수 클라이언트 로직.
- **왜**: (1) 제품 원칙 "원클릭·선택지 축소"에 자유 입력보다 태그 클릭이 더 부합.
  (2) LLM 키·지연·비용 없이 결정론적으로 동작. (3) 태그 개수를 늘려 전체 업종을 커버하려 하면
  선택지가 다시 늘어나 정체성이 깨짐 — 대신 태그 미매칭/미선택은 "아무거나"로 처리하고
  D3의 공정 셔플이 롱테일 카테고리(예: 치킨, 냉면)를 흡수한다. 커버리지보다 선택 속도 우선.
- **파생 효과**: 매칭에 서버가 필요 없어져 `/api/recommend`는 Phase 3(실데이터 조회, 키 은닉)까지
  불필요 — Phase 2는 전부 클라이언트(`app/page.tsx`)에서 처리.
- **페르소나**: 결과 카피("AI 의사 처방" 톤)도 LLM 대신 템플릿 문자열(`lib/persona.ts`)로 생성.
  선택된 태그가 있으면 카피에 반영, 없으면 일반 문구 중 랜덤.

## D6. API 키는 서버에서만
- **결정**: 공공데이터/카카오 키는 API Route(서버)에서만 사용. 클라이언트 노출 금지.
  (Anthropic 키는 D5 개정으로 v1에서 미사용)

## D7. 런타임 로깅 = console만, 외부 모니터링 서비스 없음
- **결정**: 클라이언트 에러(예: geolocation 실패)는 `console.error`로만 남긴다.
  Sentry 등 외부 에러 모니터링 서비스는 v1에서 붙이지 않는다.
- **왜**: 개인/소규모 프로젝트 단계 — 무료 티어 밖 비용·설정 오버헤드 대비 얻는 가치가 낮음.
  사용자 계정이 없어 에러를 특정 유저에 연결할 필요도 없음. 트래픽이 늘거나 운영 이슈가
  실제로 생기면 그때 재검토.

## D8. 실행 순서 재배치: Phase 4 → 공공데이터 키+Phase 3 → 카카오 고도화 (2026-07-07)
- **결정**: ROADMAP 번호(Phase 0~4)는 그대로 두되, 실제 착수 순서는
  Phase 4(상태처리/로깅, 배포 제외) → 공공데이터 키 발급 후 Phase 3 핵심(`sangwon.ts`)
  → 카카오 로컬 API 고도화(`kakao.ts`, 원래도 선택 항목) 순으로 진행.
- **왜**: Phase 4의 상태처리·로깅은 실데이터 유무와 무관하게 지금 끝낼 수 있고, 공공데이터
  키는 아직 미발급 상태라 대기 시간에 먼저 처리하는 게 합리적. Vercel 배포만은 사용자 지시가
  있을 때 진행(외부 배포는 되돌리기 번거로운 행동이라 별도 확인 필요).
